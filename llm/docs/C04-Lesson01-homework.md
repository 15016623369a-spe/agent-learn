## 第1题：时间与金额口径

题目：分别写出“最近一个月”的两种解释、订单金额的两种口径，并说明为什么需要确认。

参考答案：上一个完整自然月与向前滚动一个月并不相同。“滚动一个月”也不应自动等同于“最近30天”。以原课堂基准日2026-10-30为例，上个自然月为9月1日零点至10月1日零点之前；若明确采用日历月滚动区间，可为9月30日零点至10月30日零点之前。还需明确时区，以及按创建时间还是支付时间筛选。

金额可以采用原始订单金额、实付金额或扣除退款后的金额。例如原价120元、实付100元、退款20元，三个口径分别可能为120、100、80元。退款归属期等细节同样需要约定。本例为降低复杂度，明确限定不含退款，不代表已经建立通用退款计算规则。

系统需要确认，是因为不同解释会改变筛选集合和计算结果；不能把自己猜测的条件当成用户确认。

## 第2题：纯空白不是已提供信息

题目：把数据来源改为 `"   "`，检查状态和缺项，并解释代码。

在其余四项要求均已满足的前提下：

```python
known["data_reference"] = "   "
contract = build_task_contract(requirement, known)
```

预期状态为 `needs_info`，缺项只有 `提供订单数据或可用数据来源`。`strip()` 先把空白变为 `""`，缺项列表中的 `if not information[key]` 随后识别该值。非空 `missing` 使状态表达式返回 `needs_info`。

若同时缺少分组口径，则应有两项缺失，不能机械套用原始三字段版本的一项结果。本轮验证以其余项已明确的输入单独检查纯空白行为。

## 第4题：手写期望输出

题目：分别为缺少数据来源、信息已声明但等待核验数据，写出固定三字段 JSON。两个例子都假设其余条件已声明。

```json
{
  "status": "needs_info",
  "missing_information": ["提供订单数据或可用数据来源"],
  "next_action": "请补充订单数据或可访问的数据来源，以便后续读取并核验数据。"
}
```

```json
{
  "status": "ready_for_calculation",
  "missing_information": [],
  "next_action": "下一步读取并核验声明的数据来源，再交给计算工具执行汇总。"
}
```

这是手写预期，不是真实模型响应。助手本次将它们作为 `expected_missing`、`expected_ready` 补录到 `main()` 末尾，在入口调用前，与原有打印同级缩进。仅声明字典不会打印，需要对应 `print(json.dumps(...))`。

system 提示词只是对未来响应的要求；没有调用模型就不会自动生成响应。`input_status` 是程序任务契约字段，`status` 是约定的输出字段。二者应保持一致，但当前没有真实模型输出校验流程。
