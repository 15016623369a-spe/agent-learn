## 从生成文字到应用任务

C03 解释了 Token、模型前向计算与自回归生成。C04 开始明确应用的输入条件、输出约定、检查标准和失败处理。能生成一段文字，不代表业务任务已经完成。

贯穿请求：“请统计最近一个月各部门的订单总金额。”

先明确时间范围、时区、筛选时间字段、金额口径和数据来源。作业增加部门归属口径：按下单时所属部门，还是员工当前部门分组。

本例假设用户明确确认：

- 统计上海时区 2026-09-01 00:00:00 至 2026-10-01 00:00:00 之前的支付订单，按 `paid_at` 筛选。
- 仅统计 `status=paid`，对单位为分的 `paid_amount_fen` 求和；本教学场景不含退款。
- 按订单创建时所属部门分组，本教学场景假设 `department` 保存历史部门。
- `demo_orders.csv` 仅是明确标注的教学占位，没有创建或读取。

这些条件是教学输入，不能描述为系统自动理解、查询或核验出的事实。教学日期也不会随运行当天自动变化。

## 任务契约与程序分工

`build_task_contract(requirement, known)` 返回：

| 字段 | 含义 |
|---|---|
| task | 去掉首尾空白的用户需求 |
| known_information | 四项显式声明的信息 |
| missing_information | 按 REQUIRED 顺序列出的缺项说明 |
| input_status | needs_info 或 ready_for_calculation |
| success_criteria | 禁止猜测条件、禁止虚构执行和金额的成功标准 |

`known.get(key, "").strip()` 让缺少的键、空字符串和纯空白都成为缺项。非空字符串仅代表已声明，不保证来源存在、字段匹配或业务规则正确。

固定的缺项和状态判断由 Python 完成；模型可用于解释缺项和下一步。未来读取、计算、校验分别由对应程序或工具负责。

## 消息构造与预期输出

`build_messages(contract)` 构造一个包含 system 和 user 两条消息的列表。user 消息通过 `json.dumps` 保存任务契约；返回列表不会发送网络请求。

system 消息要求未来模型返回 `status`、`missing_information`、`next_action`。要求某种格式，不等于已经收到或验证了该格式。角色区分和文字要求也不保证防住资料中的指令，后续仍需检查与执行边界。

代码最后的 `expected_missing` 和 `expected_ready` 是助手根据第4题补录的固定手写样例，明确打印“不是模型响应”。它们假设时间、金额和分组口径都已声明，不会自动跟随 A/B/C 改变。

## 本轮实际运行结果

| 场景 | input_status | 缺项 |
|---|---|---|
| A：只有原始需求 | needs_info | 时间、金额口径、数据来源、分组口径，共4项 |
| B：时间与金额口径已确认 | needs_info | 数据来源、分组口径，共2项 |
| C：四项均已声明 | ready_for_calculation | 0项；尚未核验来源 |

每个场景 `message_count=2`。程序随后打印 C 的待发送消息和两个手写输出。完整控制台输出见 [运行输出](C04-Lesson01-output.txt)，本轮实际检查见 [验证记录](C04-Lesson01-verification.json)。

## 本次整理与边界

本课未执行模型调用、订单读取、SQL/Python 汇总、JSON Schema 校验、重试或 RAG。类型标注没有运行时校验功能，当前约定 `known` 的值为字符串；输入非字符串仍可能报错。自然语言任务没有被自动提取为结构化条件。后续在对应课程逐步扩展，不在本轮擅自加入依赖或框架。
